# 热厨：入口视线的绘制任务

`kitchen-blockout.png` 是新设计的三空间白模，不是游戏实机或目标图。`blockout.py` 在 Blender 4.2 中可重建。原 kitchen.xml 的单间另有实机留证。生图采用 **edit**，输入本 PNG；先获得同机位的目标图，再改游戏。

## 给绘图工具

在输入图上绘制一间仍能运作的老学院热厨，保持相机、主要轮廓、门窗开口、长案和右侧通道的投影位置。左侧是被熏黑的铸铁炉、挂锅和宽排烟罩，橙色余烬照出长案侧边带磨损的木纹。案上留一册翻开的油渍笔记。正面中央是传菜窗，露出垂直导轨、拉手与半收起的旧金属窗板。窗后走廊窄而暗，右侧通道尽头冷库门虚掩，冷青光落在湿地砖上。这个亮点应当引导人先看门缝，而不是照亮整个厨房。远处瓷砖纹样多重复一段，制造轻微的空间错觉。保留人物能通过的通道。低多边形、成组色块、可读剪影；按实际画面尺寸验收炉口、窗板、门缝，不作像素化。无文字、UI、轮廓高亮或场景说明箭头。

## 拿到目标图之后

1. 在项目原有的建筑编辑器里搭建三空间，保存墙体、窗洞、家具与可走路线。保留原 Godot 角色模型、动作和第三人称操作；用目标图固定入口视线、道具比例和明暗。
2. 传菜窗拉手驱动窗板沿轨道落下，终点发出碰撞声并挡住观察线；冷库门绕铰链转动，光缝随开度变宽；炉门开合露出余烬。玩家和队员交互走同一个动作和状态，不走 HUD 直接改结算。灯色与门状态来自模拟，渲染呈现它们；给色觉差异提供光脉冲节奏等第二条线索。
3. 第一条自动规则：守望者听到斩击声停止 → 拉窗。明确谁站在能听见的位置、谁获知了规则。比较手动下令、正确内化和错误内化三次现场后果；分别记录下令与执行耗时。先用时间、照明、信息暴露支撑取舍。
4. 验收保留同机位的白模、目标图、实际 Forward+ 图及操作前后帧。隐藏 UI 请观察者指认灶台、可操作窗、危险所在和可走路线；再用现有第三人称视角走一遍。核对门窗开合中途的碰撞和视线，检验光色变化能否在最低显示分辨率下辨认。

## 本机已验证的生图路径

「设计角色材质与游戏UI」使用 imagegen 技能的 `scripts/image_gen.py edit`，把实机截图发到已配置供应商的 `/v1/images/edits`。案卷和角色分别用 `gpt-image-2.5` 与 `gpt-image-2.6-sunburst` 生成过；后者使用 high。这个项目的热厨用同一条图片编辑路径，以白模代替实机截图。

从仓库根目录运行。Python 环境需要 `openai`；进程使用已有供应商的 `OPENAI_BASE_URL`、`OPENAI_API_KEY`，凭据不写入仓库、日志或提示词。把上方「给绘图工具」一段作为 `$prompt`：

```powershell
python "$HOME/.codex/skills/.system/imagegen/scripts/image_gen.py" edit `
  --model gpt-image-2.6-sunburst --quality high --size 1536x1024 --no-augment `
  --image docs/design/kitchen-paintover/kitchen-blockout.png --prompt $prompt `
  --out docs/design/kitchen-paintover/kitchen-target.png
```

检查返回的 PNG，记录实际尺寸，和入口灰模核对三个地标。正式场景还要另存同机位实机截图；两张图用途不同。历史测试中走 `/v1/responses` 曾返回 503，应检查请求的端点再判断图像服务可用性。

本轮产物：[`kitchen-target.png`](kitchen-target.png)，实际 1672×941。图中左侧炉口、中间带把手的传菜窗、右侧冷库光缝和长案笔记都可辨认。上方大面积亮灰仍像开放式布景，搭建室内时须补天花与室内光照。此图作为美术目标，不作为实机验收图。

## Lowpoly 渲染验收

以入口视线的三处轮廓定构图：排烟罩和炉口、传菜窗板和导轨、暗廊尽头的门缝。模型决定外形、遮挡、可交互开口；瓷砖缝、菱纹和釉层用世界尺度的程序高度场驱动法线、粗糙度和色差。纸张、把手和门框仍应有实体轮廓。保留原图的暖炉、暗廊、冷库三块明暗关系；冷库光由设备状态控制。

同机位锁定设备、氛围和角色，对比正午与午夜：无外窗时所有室内灯参数一致；有外窗时只调窗边入射光，物件自身光源保持原状态。内部传菜窗只传递相邻空间已有的光，不作为昼夜光源。
