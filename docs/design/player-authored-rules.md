# 小队规程：让玩家把判断教给队伍

设计提案。现有单局流程保留种子、房间连接、营地和 0–3 名随行者。现有 `FieldGuide` 用线索文本、预设选项和一次性房间结算组织遭遇；本提案先替换热厨与餐厅的信号遭遇，把答案选择改成可重复观察、可执行、可改写的规程。下文的信号装置与交互是拟加内容，现有蓝图提供空间和摆设。

## 玩家在练习什么

第一次遇见事件，队长可以亲自调查，用一次性命令试出结果。随后从记录中取出一个观察项，写成条件，再挑选队员、动作和对象。下一次遇见类似事件，队伍照做；玩家可以看它怎么判断、在哪里失败，再把例外写进去。**免费的是重复指挥：自动发令不花指令次数，也不占世界时间；队员走路、等待、调查、操作和收尾仍各自耗时。** 同一现场、同一队员、同一动作，手动与自动走同一执行路径、交同样的时间和物资成本。编写与检视规程可在暂停中完成；暂停停止遭遇时钟，动作、信号和截止时间一并冻结，恢复后才执行待发命令。驻营原生 VM 有自己的时钟，规程编辑暂停只控制远征时钟。

内化分两层。队伍内化的是一份可撤回的授权：队员在营地确认自己可以执行某个版本，出发后遇到匹配情境就代队长发令。途中发布改版时，随行队员在编辑器内确认后立即换用新版本；已开始的动作仍按旧指令完成，除非玩家明确中断。玩家内化的是从实例抽出判断方法：看见「哨声后才出汽」时，知道该先比信号和结果发生的顺序，而不是背住某间厨房的选项位置。界面让玩家利用证据编辑规程，无需先答对、攒熟练度或解锁系统认可的句子。

## 规程怎样写、怎样跑

- **触发与范围**：选择进房、观察事件或有截止时间的条件变化；范围可选本房、当前已识别的房型或所有已见到对应装置的地点。规则可设手动确认、自动执行、停用。默认新建为手动确认；发布前可用已记录事件预演，预演只显示将匹配什么、请求什么。
- **条件**：卡片可增删重排，支持 `All`、`Any`、`Not`、来源身份、计数、先后及时间窗。右值可选已识别的地标，也可引用「触发事件的来源」；跨房时重新绑定当地证据。条件只读取队伍实际观察到、尚有效的事实；事件来自有视线、可听范围或明确调查的队员。未知与过期显示 `Unknown`；`Not Unknown` 仍是未知。`All` 遇假为假、全真才真；`Any` 遇真为真、全假才假。只有真会发令。时间窗用世界时间、同一周期的事件计算；到窗尾且持续观察完整时，才可判定「窗内没有发生」。首版每次触发最多为一个执行者提交一个动作。
- **动作**：编辑执行者（指定队员、自己或最近可用随行者）、动作（移动到已见地标、调查、观察至截止、操作已见装置）、目标和参数。等距离以稳定队员顺序选人；目标有多个候选时要求选择绑定或写明选择逻辑。UI 显示路径估时、动作耗时、占用和消耗；执行器在开工和提交效果时按动作合同检查资格、距离及截止。移动和等待可取消，已流逝时间保留；交互的提交点之后只能用新的行动处理后果。首版执行请求接已有交互或原生 SimAntics 交互；缺少可调用交互时显示 `Action unavailable`，据此阻止对应内容交付。
- **错误规则可运行**：编辑器检查字段类型、缺失引用和动作是否受支持；玩家可以保存条件过宽、配错目标、顺序反了的规则。运行时照字面调度，现场按实际被操作对象、状态和时间结算。合法但危险的动作可触发警报、消耗补给或错过窗口；失败报告给出实测原因。缺目标、已失效、无可用队员、走不过去分别记录；没有「猜错所以扣血」的通用分支。规则保存和预演均不读取关卡正确选项。

### 冲突、覆写和版本

同一个世界步先收集证据并冻结视图，再评估候选、仲裁、提交请求。现场手动命令优先；随后按玩家显式排序的本房覆写、房型覆写、通用规程处理。同层按列表顺序，位置相同用稳定规则 ID 排序。覆写写明针对哪条规则：条件真时替换该条的候选，或选择 `Suppress`（本周期不派工）；覆写条件假或未知时照常评估原规则。替换动作派不出去也保留当次覆盖，避免悄悄执行被刻意拦下的旧动作。

同一队员、同一独占装置、同一遭遇的提交槽任一重叠即冲突；互不重叠可并行。胜出的请求预留所需资源；低优先级候选显示 `Blocked by …`，当次事件不偷偷排队。同一规则版本、触发事件和绑定只评估一次；已提交的遭遇槽锁至周期结束，发布新版不会重放已消费事件。新证据或下一周期可以再次触发。手动命令可以取消未开始的自动请求，或按执行器的取消合同中断在途动作。每个已提交请求固定引用版本；修改、暂停、回滚对后续候选生效，回滚以旧内容产生新版本。日志保留冲突双方、排序依据、覆写来源和执行的版本，方便玩家复盘。

## 玩家能看到什么

房内先有现象，记录才有条目。音源在场景里发声，出汽或落盘能在相应地标看见，辅助字幕标出已辨认到的来源和先后。调查台账记录观察者、地点、来源实例、周期和世界时间；重看时区分亲见、队员报告、基础设施数据缺失。规则检视器串起 `Observed → Matched → Dispatched → Started → Outcome`，另列未命中、未知、覆写、冲突、失败及耗时。玩家可以点开每个参与判定的观察；没有观察时，页面保留缺口。现场物品和后果与调度日志用同一因果 ID 关联，行文来自实际事件，静态线索文本可指路。

学院异常装置可由遭遇状态驱动，状态变化同时供画面、声源和日志消费；原生对象与人物的实际活动须从 FreeSO 读取。当前低频快照适合看摆设、位置与驻营活动，无法可靠还原相邻两拍的先后；原生时序证据如需接入，应在源头记录有顺序的事件再导出。记录绑定本局、房间实例和数据源世代；旧快照可留作历史，当前状态过期后变未知。

## 营地在队长离开后

营地是队员分享观察、确认规程、休整和自主生活的地方。远征规程默认只调度随行者；留守人员继续用原版 SimAntics 的自主机制选择活动。营地界面允许队长为下一趟指定随行名单和征询规则授权；训练或营务若需要实际执行，必须交由原版交互及其执行队列。自由意志开关、原生交互限制与离线状态都如实展示。原版营地 VM 持续运行时，队长可以离开再回来比较真实变化；关停时显示最后已知时刻，留守动作不靠 Godot 补算。首版提交的营地自主范围是「能观察原版自主活动」，营务自动委派留待有可验证执行接口时加入。

当前 `CampWatch` 已区分缺失、冻结、过期和正在推进的快照。验收时以同一营地 VM 的身份和递增 tick 为基础，用原生队列/活动来源确认自由意志发起，并核对位置、交互目标或物品变化；来源未知就标 `Activity source unknown`。队员与居民须靠经确认的稳定身份关联；房内出现的人和所有从旧档读出来的姿态分别保留自己的来源。

## 一局内外的知识

局内存事实、假设、规程版本、授权、被观察的后果和本局绑定；存档续玩保留同一世界与已消费事件。死亡、通关或用同一种子重新开局时，新建证据账、授权、队员状态与房间实例。局外保留可选的手稿和带原局标记的事后记录。手稿只携带条件结构、语义角色和动作模板，例如「两个同源事件，先看到物理变化，再响应信号」；导入后按草稿呈现，玩家在新局识别装置、重新绑定和授权。旧证据仍可阅读和比较，但规则引擎仅查询本局证据。即使同种子重开，玩家记住的答案也得经当前观察、亲自命令或现地绑定转化成行动。

## 可证伪样板：热厨学到的规程在餐厅失手

地块用 `kitchen.xml` 与 `dining.xml`。热厨原有地标为炉灶 `(14,13)`、备餐台 `(15–17,13)`，经 `(13,17)` 门槛进房；餐厅可用 `(10,10)` 门槛入场、以 `(12,13)` 的现有餐桌作为回声源。坐标使用 `plan_landmarks.json` 的零基地板层约定。新增的送话管与交付点是遭遇锚点：热厨送话管放在备餐台一端；餐厅把交付点放在靠入口餐桌的可达一侧，与桌面回声区分。先在实机核对视线、声源分离与可达性。两个房型由拓扑生成，可跨其他房间实验；验收选一个经生成确认两者均可达的固定种子，记录种子、路线和房间实例，另以固定事件夹具核对数值。

每房调查后可在标记地标旁启动下一周期；同一周期只允许提交一次，失败可等周期结束后重试，损失保留。样板时钟以周期起点为 `t=0`，每拍为一秒有效世界时间。为对照将同一执行者放在两目标共同交互范围内，交互用时 `1` 拍，触发与派工同拍，接受窗口截止到 `t=4`（含）。实机若两个交互范围不能重叠，先调整拟加锚点，或在夹具记录固定行走时间并等量平移预期提交时刻。每行均为玩家亲眼或队员在视听范围内实际观察的事件。

| 地点 | 可观察事件 | 实际操作结果 |
| --- | --- | --- |
| 热厨 | `t=1` 炉灶水壶出汽；`t=2` 水壶鸣响；`t=3` 送话管鸣响；`t=4` 管口出汽。 | 操作水壶在 `t=3` 完成则点亮通过灯；操作送话管在 `t=4` 完成则触发警报，本周期扣 1 点样板生命。 |
| 餐厅 | `t=1` 桌子响，未见落盘；`t=2` 交付点落盘且同时响铃。 | 操作桌子在 `t=2` 完成则触发警报并消耗本周期提交槽；操作交付点在 `t=3` 完成则取到盘子。 |

1. **先教一个够用的办法。** 在热厨手动操作水壶，记下出汽和鸣响。写 `R1: On audible cue → Operate cue source`，用相同初态跑下一周期：`t=2` 由水壶第一次触发，`t=3` 成功；管声记录为槽已使用。对照组由玩家在 `t=2` 手动命令，比较开始时间、完成时间、在场画面与结果；唯一差异是发令来源与玩家是否需要再次点击。
2. **带去餐厅，允许它犯错。** 对本房绑定已辨认的来源后保留 `R1`。桌响先触发，`t=2` 操作桌子导致警报；落盘与响铃仍实际出现，交付点因本周期槽已被占用而未取。日志可指回桌响发生时缺少的物理证据。编辑器允许发布这条会失败的规则。
3. **写出例外，再回抽通用条件。** 给 `R1` 加本房覆写：观察到交付点落盘时操作交付点；另配本房 `Suppress` 兜底，禁止旧规则响应其他声音（同优先层将落盘替换排在兜底之前；落盘和铃声同拍时，先收集两项再仲裁；仅有落盘而无铃时，替换也可独立触发）。下一周期 `t=1` 忽略桌响，`t=2` 派工、`t=3` 取盘。随后关闭例外，改成 `R2: On audible cue, if a physical change from that same source was observed in this cycle [cue−1 beat, cue], operate cue source`。端点含等号，源绑定为已观察实例。热厨与餐厅各跑一遍：水壶与交付点分别在 `t=3` 完成；用固定夹具调换热厨管声和水壶声的先后（管声 `t=1`、管汽仍 `t=4`），`R1` 应在 `t=2` 触发警报，`R2` 应等到水壶。再隐藏炉灶出汽的视线并保持真实出汽，`R2` 对水壶显示 `Unknown`，没有派工。上述变化任一产出相同的动作轨迹，便有可定位的实现缺陷。

覆写的触发由它自己的事件定义；它可独立提出替换候选。每拍以该覆写在同一范围内已见证据对被指向规则仲裁，`Suppress` 兜底只抑制原候选。样板的取盘动作因此也能对仅落盘的变体派工，而同拍落盘和铃声只派出一次。每周期重置判定上下文，上一周期落盘不能替代本次观察。

## 验证与交付门槛

| 要检查什么 | 通过标准 |
| --- | --- |
| 无头事件轨迹 | 固定事件和初态下，重放得到相同的证据顺序、候选、资源预留、版本及提交结果。覆盖未知和否定、同拍落盘、过期、跨源/跨周期、时间窗边界、两个队员竞争同一槽、同队员两任务、互不冲突并行、手动抢占、覆写兜底、替换不可执行、不自动回退和回滚。 |
| 世界时钟和真实代价 | 暂停编辑前后时钟、移动和截止均一致；手动与自动同条件同结果；将执行者移远，使路径加交互越过 `t=4`，自动照样逾期；途中取消保留已用时间，已提交的效果仅发生一次。 |
| Forward+ 实机 | 走到两处现有地块，用正式输入完成调查、写错、看到警报、加覆写、改为通用条件、回放证据。用游戏 MCP 保留对应截图和可比对的事件日志；同时核对声音/字幕、出汽/落盘、执行者移动及物品状态。至少做一次在视线外或听距外的对照。 |
| 原版营地 | 实机启动已绑定营地的 FreeSO VM，留守且无人下令，捕获至少一次来源明确的自主交互和可见结果。再关停或暂停 VM，验证过期状态，无新增营务完成记录；恢复或更换进程后以新鲜身份、tick 与实际活动重新建立证据。 |
| 生命周期 | 续存保持已消费事件和版本；同种子重开和换种子开局均清空局内证据及授权，导入手稿停在草稿，完成重新绑定才可自动运行。保留一条旧局报告，确认它无法满足新局条件。 |
| 盲测内化 | 给玩家热厨例子及规程编辑器，不预告餐厅答案。记录能否由现场或日志指出失败的原因、亲手改出覆盖规则，并在换序夹具里提前说出会派谁、对何物、在何时。分别记录预测、实际结果及误判原因；以玩家能解释并迁移为目标，不以找到现成模板算通过。 |

首版交付止于两处遭遇、一个可编辑规程板、一份可追溯证据账和可核验的原版营地观察。现有房间的选项式内容可与样板并存；通关仍遵循当前流程，样板的证据与旧有收集条件如何衔接应在扩展前另定。
