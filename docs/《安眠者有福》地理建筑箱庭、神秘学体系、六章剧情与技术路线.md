## 第四部分：C# Core 与 DV 内容技术路线

游戏采用 C# Core 与 DV 内容分层，CLI 和 Godot 共用同一会话与演算机制；但是宿主分别承担文本输入输出与真实场景呈现，Godot 的移动、碰撞和阅读状态仍须在真实窗口验证。

### 一、内容与解释职责

剧情、人物倾向、认知初值、认知参数、接纳规则、物体属性、房间拓扑及世界法则由 `.dv` 声明；但是解析、条件求值、效果应用、证据更新、主观推理和行动调度统一由 C# 实现。旧章节的兼容编译前端继续读取既有 DV 内容；但是编译器本身以 C# 维护，自举和固定点构建保持废弃。

### 二、时间与模拟

呈现帧、环境推进、人物决策和昼夜结算可以按职责采用不同频率，频率和扩散参数由内容提供；但是固定 60 Hz、1 Hz、15 分钟周期与毫秒耗时属于待测目标，不能当作已经实现的性能保证。房间拓扑、门窗、源质浓度和高度差参与环境演算；但是扩散模型需满足边界、非负性和来源约束，实际采用的公式以 Core 实现及 DV 参数为准。

### 三、认知、保护规则与实体资源

每个人物通过自身观察、交谈和证据形成认知，事实保留来源与冲突状态；但是单一知情位掩码无法表达误解、争议与信念强度，因此掩码只适合作为经过等价验证的派生索引。注册身份与群体成员资格由 DV 声明；但是固定低 16 位的常量不能替代内容中的实际成员。

恶魔的保护义务、触发条件、作用范围和持续时间由 DV 声明，Core 以通用条件、动作与资源占用机制执行；但是“一个房间占用后另一处必然杀人成功”需要完整验证规则优先级、可达动作和人物认知，不能直接写成机制结论。

应急脱扣杆、门闩和逃生路径作为 DV 世界物体及规则参与演算，Godot 负责对应的几何呈现和运动；但是碰撞穿透会改变世界可达性，应以正式动作和规则明确授权，避免显示结果与 Core 状态分离。

### 四、验证与实际覆盖

CLI 与 Godot 均保持自动测试及 AI 测试入口，自动入口由引擎 AI 持续运行，AI 入口由代理依据新观察逐步操作；但是人工和单场景检查仍复用正式输入接口，完整通关须依据实际结束状态。现有实现与运行命令以 `游戏结构.md` 为准；但是六章内容规划和上述优化目标继续作为设计目标，性能与覆盖结论随正式 MCP 报告更新。
