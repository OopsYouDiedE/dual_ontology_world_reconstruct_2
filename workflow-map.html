先记住四件事

① 游戏自己运行

玩家打开 Godot，标题进入正式游戏。主线、房间、互动与存档由游戏进程处理。

② 测试启动游戏

评估 MCP 把任务交给 worker，worker 启动独立 Godot 执行快检并保存结果。

③ 评审保存证据

评审 MCP 记录修改、检查、盲读和评分；需要时汇总成报告。

④ 其他工具按需运行

生活模拟、建筑控制、录制和单项探针各自有入口；平时游戏启动不会自动跑完整套测试。

展开：MCP 与普通游戏的关系

BuildingMcp 和 GameMcp 在 project.godot 中属于自动加载节点。它们在没有专用端口参数时关闭处理；通过相应 MCP 启动并提供端口和令牌时，才在本机开启控制通道。音频、设置和语言自动加载项则服务普通游戏。

哪些当前没有使用？

按“在哪条工作流运行”来判断，比单纯数引用更可靠。以下是可核对的具体结果：

对象当前状态证据与含义
GameControl.gd / GodotControl.gd 的 TCP 通道普通启动时休眠两个 _ready() 在端口为 0 时关闭处理；带各自 MCP 参数才监听。节点仍由项目自动加载。
mcp/game/server.py、mcp/building/server.py当前项目 MCP 配置未注册；按需入口存在game 客户端和建筑 client 会自行启动它们；不能据此判为废弃。
mcp/eval/ 第二套方案尚未接入，目录当前不存在goal.md 明确选择 mcp/evaluation/，第二套仅为评估设计。
tools/testing/wardrobe_probe.gd单项测试入口，平常主线启动不运行fast_checks.json 列出该探针；按测试调度时使用。
tools/testing/run_parallel.py、run_fixture.py独立开发工具，按需运行两者各自启动 review watcher；当前 evaluation 工作流另由 worker.py 调度。

文件级完整候选可在代码清单查看入边为 0 的文件。独立启动脚本、命令行入口、引擎回调、动态路径和构建系统隐式引用也可能没有静态入边，因此清理前应再核对配置、运行日志与历史用途。
